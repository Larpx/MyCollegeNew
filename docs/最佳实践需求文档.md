
# Campus.Attendance 项目最佳实践要求文档
本文档定义了基于 .NET 10 开发 Campus.Attendance 系统（包含 Web UI 和 RESTful API）的架构规范与最佳实践。所有代码编写与提交必须遵循以下标准。
## 1. 技术栈选型
*   **核心框架**: .NET 10、ASP.NET Core 10
*   **API 风格**: Minimal APIs (轻量级，配合垂直切片架构)
*   **前端框架**: Blazor Web App (.NET 10 统一交互模型：静态 SSR + 交互式 Server/WebAssembly)
*   **架构模式**: 垂直切片架构 + CQRS (命令查询职责分离)
*   **中介者模式**: MediatR (用于实现 CQRS 和管道行为)
*   **数据验证**: FluentValidation (替代 DataAnnotations)
*   **对象映射**: Mapster (性能优于 AutoMapper，编译时生成)
*   **日志系统**: Serilog (结构化日志)
*   **ORM框架**:  SQLSugar (性能优化，支持多数据库)
*   **API 文档**: 内置 `Microsoft.AspNetCore.OpenApi` + Scalar (现代化 UI)
*   **缓存方案**: Redis + `IDistributedCache` (支持配置切换为内存缓存)
*   **认证授权**: ASP.NET Core Identity + JWT (API 端) + Cookie (Web 端)
*   **测试框架**: xUnit + FluentAssertions + Moq
*   **本地编排**: .NET Aspire
## 2. 项目结构与架构原则 (基于 VSA)
采用**垂直切片架构 (VSA)**，按业务功能切分代码，而非按技术类型分层。每个功能模块内包含自身的 Endpoint、Handler、DTO 和 Validator。
### 2.1 项目结构
```text
Campus.Attendance.sln
├── src/
│   ├── Campus.Attendance.Api/          -> API 入口项目 (Minimal APIs, 中间件, DI 注册)
│   │   ├── Features/                   -> 垂直切片核心目录
│   │   │   ├── Attendance/             -> 考勤功能模块切片
│   │   │   │   ├── Domain/             -> 该切片专属的领域实体 (可选)
│   │   │   │   ├── CreateAttendance/   -> 创建考勤功能
│   │   │   │   │   ├── CreateAttendanceEndpoint.cs  (Minimal API 路由)
│   │   │   │   │   ├── CreateAttendanceCommand.cs   (CQRS 请求)
│   │   │   │   │   ├── CreateAttendanceHandler.cs   (业务逻辑)
│   │   │   │   │   ├── CreateAttendanceValidator.cs (FluentValidation)
│   │   │   │   │   └── AttendanceDto.cs             (响应 DTO)
│   │   │   │   └── GetAttendance/      -> 查询考勤功能
│   │   │   └── Users/                  -> 用户功能切片
│   │   └── Contracts/                  -> 全局共享的基础接口
│   ├── Campus.Attendance.Web/          -> Blazor Web App (UI 组件, 调用 API 的 HttpClient)
│   ├── Campus.Attendance.Shared/       -> 共享内核
│   └── Campus.Attendance.Infrastructure/ -> 基础设施实现 (EF Core DbContext, Redis 连接, 邮件发送等)
└── tests/
    ├── Campus.Attendance.UnitTests/    -> 针对 Features 下的 Handler 测试
    └── Campus.Attendance.IntegrationTests/ -> 针对 API 端到端测试
```
### 2.2 核心架构原则
1.  **高内聚低耦合**：修改某个功能（如“请假”）时，所有需要变动的代码必须位于该功能的切片文件夹内，避免跨项目、跨文件夹的“散弹式修改”。
2.  **共享内核与防重复**：**（强制）** 提取跨切片的公共代码（如基础实体接口 `IAuditable`、通用枚举、分页请求基类 `PagedQuery`、自定义异常类）至 `Campus.Attendance.Shared` 共享内核项目中，或通过抽象基类进行管理，坚决避免在多个切片中复制粘贴相同的底层逻辑或基础 DTO。
3.  **切片间通信**：切片之间禁止直接引用内部的 Handler 或 Service。如需跨功能调用，必须通过 MediatR 发送请求，或通过定义在共享内核中的接口进行调用。
## 3. RESTful API 开发规范
1.  **路由与参数**：使用 Minimal APIs 扩展方法按模块注册路由（如 `app.MapAttendanceEndpoints()`）。明确参数来源，使用 `AsParameters` 特性绑定 Query 和 Body。
2.  **API 版本控制**：强制使用 `Asp.Versioning.Mvc` 和 `Asp.Versioning.Mvc.ApiExplorer` 包。采用 URL 路径版本控制（如 `/api/v1/attendances`）。
3.  **统一响应与错误处理**：
    *   使用 `IExceptionHandler` 接口集中捕获全局异常，返回标准的 `ProblemDetails` (RFC 7807) JSON。
    *   **禁止**返回 `IEnumerable`（应返回 `IAsyncEnumerable<T>` 实现流式序列化）。
    *   **禁止**直接将领域实体暴露给 API。
4.  **HTTP 语义**：严格遵循 GET (查询), POST (创建), PUT (整体更新), PATCH (部分更新), DELETE (删除)。正确使用状态码：200, 201 (Created), 204 (No Content), 400, 401, 403, 404。
5.  **契约优先 (DTOs + 映射)**：使用 `CreateAttendanceRequest` 和 `AttendanceResponse` 等 DTO。使用 Mapster 进行映射。
6.  **异步贯穿始终**：Endpoint Handler 和 MediatR Handler 必须声明为 `async Task<IResult>` 或 `async Task<T>`，并接收 `CancellationToken` 参数。
## 4. Web UI 与 API 交互规范
1.  **Blazor 渲染模式**：默认使用静态 SSR 渲染页面，仅在需要高交互（如拖拽、实时图表）的组件上开启 `@rendermode InteractiveServer` 或 `InteractiveWebAssembly`。
2.  **HTTP 调用**：Web 项目调用 API 时，必须使用 `IHttpClientFactory` 结合命名客户端或类型化客户端。
3.  **身份认证联动 (BFF 简化模式)**：
    *   **后端 API**：使用 JWT Bearer Token 认证。
    *   **前端 Blazor**：使用 **Cookie 认证**。Blazor 服务端接收用户账密后向 API 请求 Token，然后将 Token 写入 **HttpOnly Cookie** 中。**绝不将 JWT 存入 localStorage**。后续 Blazor 发起请求时自动携带 Cookie，由服务端拦截器提取 Token 并附加到向 API 发送的 `Authorization: Bearer` 请求头中。
## 5. 关键基础设施与工程规范
1.  **OpenAPI 文档**：使用内置的 `Microsoft.AspNetCore.OpenApi` 生成 `openapi.json`。UI 界面弃用 Swashbuckle，改用 **Scalar**。
2.  **依赖注入生命周期**：MediatR Handlers、DbContext、业务服务注册为 `Scoped`。`HttpClientFactory`、配置选项注册为 `Singleton`。
3.  **配置强类型化**：禁止直接 `Configuration["Key"]`，必须使用 Options Pattern (`IOptions<T>`, `IOptionsMonitor<T>`)。
4.  **数据校验分离**：禁用 DataAnnotations (`[Required]` 等)。DTO 保持为纯 POCO，为每个 Command/Query 编写独立的 `FluentValidation` 验证器，通过 MediatR Pipeline Behavior 自动执行校验，失败则返回 400 ProblemDetails。
5.  **认证与授权双轨制**：配置双认证方案。`/api` 路径默认使用 `JwtBearer`；`/` (Web 路径) 默认使用 `Cookie`。使用基于策略的授权控制 API 权限。
6.  **安全防护**：明确配置 CORS 白名单。强制 HTTPS 重定向和 HSTS。Blazor 表单提交必须使用内置防伪令牌 防范 CSRF。
7.  **取消令牌支持**：所有 I/O 操作使用 `async/await`，并在 Endpoint 和 Handler 签名中接收并传递 `CancellationToken`，支持客户端断开连接时取消数据库查询。
8.  **缓存策略**：使用 `IDistributedCache` 抽象。通过配置文件切换实现：生产环境用 Redis，测试环境用 `MemoryDistributedCache`。对高频只读 API 启用 `OutputCache` 中间件。
9.  **响应压缩**：默认启用 Brotil 和 Gzip 响应压缩中间件。
10. **限流**：使用内置 `System.Threading.RateLimiting` 中间件，针对不同角色或 API 配置不同的并发/令牌桶限流策略。
11. **日志与可观测性**：Serilog 配合 `Serilog.Sinks.Async` 异步写入文件/数据库。集成 `OpenTelemetry`，将 Traces 和 Metrics 发送到 Aspire Dashboard 或 Jaeger。
12. **配置与机密管理**：`appsettings.json` 结合环境变量。本地开发敏感数据使用 .NET User Secrets；生产环境使用 Azure Key Vault 或环境变量注入。
13. **.NET Aspire 编排**：本地开发时，使用 Aspire AppHost 项目统一拉起 Api、Web、本地 Redis 容器和 SQL Server 容器，自动处理服务发现和连接字符串注入。
